# Error Analysis

To obtain a comprehensive understanding of database design errors, we conducted a fine-grained analysis of the database designs generated by DBGenie with three backbone models. Following the principles of open coding, we systematically categorized all identified errors to uncover recurring error patterns and their underlying causes. Each backbone model was evaluated on 51 tasks, yielding 153 samples in total.

All error annotations were performed by three domain experts with expertise in database systems and software engineering. For each sample, two experts independently examined the corresponding requirement, access patterns, and generated DDL. When their judgments differed, the third expert served as an adjudicator and determined the final label. Before adjudication, we measured agreement between the two primary annotators using Cohen's kappa. The overall inter-annotator agreement was \(\kappa=0.92\).

We grouped the identified database design errors into five primary categories: Entities and Attributes, Relationships and Semantics, Integrity and Business Rules, Physical Design, and Structure and Maintainability. Each primary category was further divided into several secondary categories.

## 1. Entities and Attributes (50.75%)

This category captures cases in which a database design fails to represent the core business objects and their information completely and accurately.

- **Missing Core Entities:** An independent business object explicitly required by the specification has no corresponding table or equivalent structure.
- **Incomplete Entity Information:** An entity lacks required key attributes, state information, or historical information.
- **Attribute Representation Mismatch:** The storage format or value semantics of an attribute cannot correctly represent the requirement.

In sample `deepseek::Ctrlpanel-gg__panel`, access pattern w5 explicitly requires a support request to include a description and an urgency level:

> Open a new customer support request, including subject, description, urgency level, the user's identity, and the department it belongs to.

However, the generated table contains neither field:

```sql
CREATE TABLE `support_tickets` (
  `id` BIGINT NOT NULL AUTO_INCREMENT,
  `user_id` BIGINT NOT NULL,
  `department_id` BIGINT NOT NULL,
  `subject` VARCHAR(255) NOT NULL,
  `status` VARCHAR(20) NOT NULL,
  `created_at` DATETIME NOT NULL,
  `updated_at` DATETIME NOT NULL,
  `closed_at` DATETIME,
  PRIMARY KEY (`id`),
  CONSTRAINT `fk_support_tickets_user` FOREIGN KEY (`user_id`) REFERENCES `users` (`id`),
  CONSTRAINT `fk_support_tickets_department` FOREIGN KEY (`department_id`) REFERENCES `departments` (`id`),
  CONSTRAINT `chk_support_tickets_status` CHECK (`status` IN ('open','in_progress','closed'))
) ENGINE=InnoDB;
```

Although `support_tickets` stores the subject, user, and department, it omits both the required description and urgency level. The design therefore cannot preserve all information needed to create a support request and constitutes incomplete entity information. This error indicates that the current method does not yet decompose and verify requirements sufficiently and may therefore omit essential entity information.

## 2. Relationships and Semantics (21.64%)

This category captures cases in which associations, ownership boundaries, or lifecycle relationships between entities fail to express the intended business semantics.

- **Incomplete Entity Associations:** A required association is not fully established, preventing records from being reliably linked to their target entities.
- **Incorrect Ownership Boundaries:** A record lacks the correct owner or tenant boundary and may therefore reference data outside its intended scope.
- **Incomplete Lifecycle Modeling:** State transitions, version relationships, or historical processes are not fully preserved.
- **Incorrect Relationship Cardinality:** The optionality or cardinality of an entity relationship, such as one-to-one or one-to-many, conflicts with the requirement.

In sample `deepseek::BeatLeader__beatleader-server`, access pattern w16 requires displaying a player's selected badges, prestige rewards, and decorative assets:

> Show a player's selected profile presentation, including badges, prestige rewards, avatar or decorative assets, and social links.

The generated DDL defines the profile-presentation table as follows:

```sql
CREATE TABLE profile_presentations (
    id BIGINT NOT NULL IDENTITY(1,1) PRIMARY KEY,
    player_id BIGINT NOT NULL REFERENCES players(id),
    CONSTRAINT UQ_profile_presentations_player_id UNIQUE (player_id)
);
```

The table references only the player and provides no association with the selected badges, prestige rewards, or decorative assets. It therefore cannot store the presentation relationships required by the access pattern and constitutes an incomplete entity association. This error indicates that the current method can identify major entities but does not yet derive relationship semantics, including ownership, cardinality, and lifecycle, consistently.

## 3. Integrity and Business Rules (8.21%)

This category captures cases in which constraints or other database mechanisms fail to enforce data validity and key business rules effectively.

- **Key Constraint Defects:** Primary-key or uniqueness constraints fail to represent record identity or business-level uniqueness correctly.
- **Attribute Constraint Defects:** Missing or incorrect nullability, check, or domain constraints either permit invalid data or reject valid data.
- **Missing Cross-Record Constraints:** A business rule involving multiple records lacks a corresponding database constraint or maintenance mechanism.

In sample `qwen::Tbeninnovation__Baiss`, the requirement calls for storing multiple response alternatives for a message:

> The database must support an AI assistant application that stores user conversations, individual messages, selected response alternatives, and the search-path evidence used by RAG-style answers.

The generated DDL restricts each message to a single response alternative:

```sql
CREATE TABLE "response_alternatives" (
  "id" BIGINT NOT NULL GENERATED BY DEFAULT AS IDENTITY,
  "message_id" BIGINT NOT NULL,
  PRIMARY KEY ("id"),
  UNIQUE ("message_id"),
  FOREIGN KEY ("message_id") REFERENCES "messages"("id")
);
```

The `UNIQUE ("message_id")` constraint allows at most one response alternative for each message, contradicting the requirement for multiple alternatives and constituting a key constraint defect. This error indicates that the current method focuses more strongly on producing executable schemas than on consistently translating natural-language business rules into database constraints.

## 4. Physical Design (9.70%)

This category captures cases in which indexes and other physical structures fail to support the access patterns specified in the workload effectively.

- **Missing Index Support for Access Patterns:** A key access pattern in the workload lacks an effective supporting index.
- **Index-Access Pattern Mismatch:** An index exists, but its leading columns, column combination, or column order does not match the query conditions.
- **Low-Value Indexes:** An index duplicates another index or provides no clear benefit for the given workload, adding only storage and write-maintenance overhead.

In sample `qwen::BeatLeader__beatleader-server`, access pattern w4 requires listing all alias requests awaiting review together with their submission times:

> Find all alias requests that are still awaiting review, with the requesting player and submission time.

The generated DDL defines the relevant index as follows:

```sql
CREATE INDEX [IX_aliases_player_status] ON [aliases] ([player_id], [status]) INCLUDE ([alias_value], [submission_time]);
```

The query must first filter all records by `status = 'pending'`, but the index begins with the leading column `player_id`. When no player is specified, the index cannot efficiently locate pending records and therefore exhibits an index-access pattern mismatch. This error indicates that although the current method can generate indexes, it remains limited in deriving appropriate column combinations, leading columns, and column order from access patterns.

## 5. Structure and Maintainability (9.70%)

This category captures data representations that increase the complexity of querying, integrity maintenance, or future schema evolution.

- **Improper Storage of Multi-Valued Structures:** Multi-valued information that requires independent querying or constraints is encapsulated in a single text or JSON column.
- **Polymorphic Associations:** A shared type field and identifier field refer to multiple entity types, making it difficult for the database to enforce target existence through foreign keys.
- **Duplicate or Conflicting Representations of the Same Fact:** The same business fact is stored in multiple locations, creating potentially inconsistent sources of truth.

In sample `qwen::DogukanUrker__FlaskBlog`, the requirement calls for storing the view count of each blog post:

> Blog posts should include authored content, presentation metadata, categories or tags, public URL information, edit history, and view counts.

The generated DDL stores the same count in two locations:

```sql
CREATE TABLE blog_posts (
    id INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
    -- ...
    view_count INTEGER DEFAULT 0,
    -- ...
);

CREATE TABLE view_counts (
    id INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
    view_count_value INTEGER DEFAULT 0,
    last_updated DATETIME,
    blog_post_id INTEGER NOT NULL UNIQUE,
    FOREIGN KEY (blog_post_id) REFERENCES blog_posts(id)
);
```

Each post's view count is stored in both `blog_posts.view_count` and `view_counts.view_count_value`, while the DDL provides no mechanism to keep the two values synchronized. The design may therefore create two conflicting sources of truth. This error indicates that the current method sometimes favors flexible or generic representations without sufficiently accounting for referential integrity, a single source of truth, and long-term maintenance costs.
